# تشغيل مستخدمي العيادة من داخل التطبيق وطابور الاستقبال

## مسار العمل (الإصدار 1.3)

| المستخدم | الصلاحيات |
|---|---|
| المدير (admin) | يرى الأطباء ويُنشئ حساب طبيب عبر الاسم الكامل واسم المستخدم وكلمة المرور. يقدر يعيد تعيين كلمة مرور طبيب أنشأته الإدارة |
| الطبيب (doctor) | يرى مرضاه وطابوره، ويُنشئ حساب سكرتير مرتبطاً بطبيبه وحده، أو يغيّر كلمة مروره |
| السكرتير (secretary) | يُضيف اسم مريض لطابور طبيبه فقط، ويقدّم/يؤخر الأسماء، ويحدّد الانتظار والدخول والانتهاء والإلغاء |
| الطبيب (تسجيل ملف مريض) | يضغط «إضافة كملف طبي» بجانب اسم موجود بالطابور. الاستمارة تفتح والاسم مُعبّأ، يكمل DOB، الجنس، معلومات وليّ الأمر، التاريخ الطبي... ويحفظ، ثم يُربط الملف بسطر الطابور |

السكرتير **لا يستطيع** إنشاء ملف طبي كامل أو الاطلاع على التشخيص والفحوص والوصفات، ولا اختيار طبيب غير المعيّن له.

## المخطط الأساسي

- تأكيد الجداول حسب `001_initial_schema.sql`.
- تطبيق `002_role_and_record_security.sql`.
- تطبيق `003_secretary_and_clinic_queue.sql` الذي ينشئ role secretary والطابور وRPCs.
- تطبيق `004_staff_creation_and_queue_records.sql` الذي ينشئ خريطة أسماء المستخدمين ويربط سطر الطابور بالملف الطبي.

**مهم:** لا تشغّل هذه الترحيلات عشوائياً على بيانات موجودة. افحص في Staging أولاً. إذا ما تحتاج البيانات القديمة، استخدم **مشروع Supabase جديد/تجريبي** وجداول جديدة بدلاً من حذف مشروع العيادة الحالي بدون نسخة احتياطية.

## تفعيل إنشاء الحسابات من التطبيق

1. في Supabase Dashboard افتح SQL Editor واختبر وطبّق الترحيلات بالترتيب.
2. افتح Edge Functions وانشر `supabase/functions/provision-staff/index.ts` باسم **provision-staff**. عند استخدام CLI:
   ```bash
   supabase login
   supabase link --project-ref YOUR_PROJECT_REF
   supabase functions deploy provision-staff
   ```
3. تحتاج وظيفة Edge Function فقط إلى متغيرَي البيئة على **الخادم**: `SUPABASE_URL` و`SUPABASE_SERVICE_ROLE_KEY` (موجودان ضمن بيئة Supabase Edge Functions). **لا تضف service-role إلى GitHub Actions الخاص ببناء APK ولا إلى Flutter**.
4. فعّل التحقق من JWT للوظيفة واجعلها تقبل جلسة مستخدم مسجّل دخوله، لا اتصالاً مجهولاً.
5. لإنشاء حساب المدير **أول مرة فقط**: أنشئ الحساب عبر Authentication → Users، ثم SQL Editor تحت صلاحية الإدارة:
   ```sql
   update public.profiles set role = 'admin'
   where id = '<YOUR_ADMIN_AUTH_USER_UUID>';
   ```
   تأكّد أنه الحساب الصحيح قبل منحه الدور. الإدارة لا تُمنح بتسجيل عام.
6. سجّل دخول المدير في التطبيق وأضف الطبيب عن طريق **إضافة طبيب**. حساب الطبيب سينشأ في Supabase Auth وتضاف بياناته إلى `doctors`.
7. سجّل دخول الطبيب عن طريق **اسم المستخدم** وكلمة المرور، ثم اضغط **إضافة سكرتير**؛ ستُنشأ علاقة ثابتة بطبيبه في `secretary_assignments`.
8. سجّل دخول السكرتير وسيظهر له طابور الطبيب مباشرة.
9. أدخل اسماً وهمياً لطابور اليوم، وراقب ظهوره عند الطبيب بعد تحديث الشاشة. الطبيب يضغط **إضافة كملف طبي** ويدخل المعلومات الناقصة ويحفظ.

### اسم المستخدم وكلمة المرور

- اسم المستخدم من 4 إلى 24 رمزاً لاتينياً صغيراً، يبدأ بحرف وقد يحتوي أرقاماً أو `_`.
- الـEdge Function يخصص عنوان بريد **داخلي غير قابل لاستلام الرسائل** بصيغة `username@staff.yadati.invalid`، لا يحتاج المستخدم لمعرفة هذا العنوان أو إدخاله. هذا حل حسابات موظفين، وليس وسيلة تسجيل عبر بريد فعلي.
- يجب استخدام كلمة مرور قوية من **12 إلى 128 رمزاً**. لا تُحفظ بقاعدة بيانات التطبيق؛ يتولى Supabase Auth تخزين تجزئتها.
- عند النسيان، يعيد المدير تعيين كلمة مرور الطبيب، أو يعيد الطبيب كلمة مرور سكرتيره من داخل صفحة **حسابات العاملين**. هذه الحسابات لا تدعم استعادة البريد لأن عنوانها داخلي. احتفظ بوصول آمن لحساب المدير.
- قد ترفض بعض إعدادات Auth نطاق البريد الداخلي الافتراضي؛ **اختبر إنشاء مستخدم واحد داخل Staging قبل الإنتاج**. وإذا رفضه Supabase، انتقل إلى استخدام بريد حقيقي بدلاً من تغيير النطاق إلى عنوان لا تملكه.
- تفعيل MFA وتسجيل تدقيق التغييرات وإيقاف الحسابات عند مغادرة الموظف تحسينات مطلوبة قبل نشره على نطاق واسع.

## اختبار التكامل المطلوب

- مدير واحد يستطيع إنشاء طبيب؛ الطبيب يستطيع تسجيل الدخول، والطبيب لا يستطيع إنشاء طبيب آخر.
- الطبيب ينشئ سكرتيراً واحداً مربوطاً به؛ السكرتير لا يستطيع إنشاء سكرتير أو طبيب.
- منع السكرتير من قراءة `patients`، `examinations`، `prescriptions`، `media_files` لأي مستخدم.
- الطبيب A والسكرتير A لا يمكنهم الوصول إلى طابور الطبيب B.
- السكرتير يضيف مريضاً إلى الطابور دون إنشاء سجل `patients`.
- الطبيب A يُحوّل اسم الطابور إلى ملف طبي كامل مرتبط بطبيبه فقط.
- السكرتير لا يستطيع تنفيذ RPC `link_clinic_queue_patient` حتى لو عرف UUID.
- عند تعثر عملية الربط بعد حفظ الملف، يظهر تنبيه للطبيب بأن الملف محفوظ دون ارتباط تلقائي؛ لا تُفقد البيانات ولا يُنشأ ملف ثانٍ تلقائياً.
- يستطيع المدير/الطبيب إعادة تعيين كلمات مرور حساباتهم التابعة فقط.
- لا تسلّم بيانات مرضى حقيقية قبل انتهاء اختبار سياسات RLS وإجراءات النسخ الاحتياطي.

راجع أيضاً `docs/SECRETARY_QUEUE_SETUP.md` لمزيد من اختبارات تقييد طابور الطبيب.
